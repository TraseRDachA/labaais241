# Анализ бэкенда (Node.js Express) и дорожная карта доработок

Данный документ содержит результаты аудита серверной части после подтягивания ветки `alphabackend`, статус интеграции фронтенда и бэкенда («поженили»), а также перечень недостающего функционала для полноценной работы и защиты информационной системы «Учет успеваемости студентов».

---

## 1. Что было сделано при подтягивании и интеграции

### 1.1. Синхронизация ветки `alphabackend`
- Выполнен `git fetch origin` и fast-forward слияние ветки `origin/alphabackend` в локальную ветку `main`.
- Удален случайный артефактный файл `-Method`, оставленный ошибочной CLI-командой в коммите бэкенда.
- Установлены зависимости бэкенда в папке `backend/` (`express`, `cors`, `bcryptjs`).
- Выполнено первоначальное наполнение базы данных через `seed.js` и сгенерированы расширенные оценки через `addMoreGrades.js` (более 360 оценок по всем 5 семестрам, дисциплинам и группам).

### 1.2. Исправление критических багов на бэкенде
1. **Баг парсинга токена в `backend/middleware/auth.js`**:
   - Предыдущий регулярное выражение `^fake-token-([^-]+)-(\d+)$` ломалось на любых идентификаторах, содержащих дефис (например, `u-1`, `u-2`, `u-3`, `u-4`).
   - Из-за этого `extractUserFromToken` всегда возвращал `null`, `req.user` оставался пустым, все действия в аудит-логе писались как «Аноним», а в панели администратора срабатывала ошибка или разрешалось удаление собственной учетной записи администратора.
   - Регулярное выражение исправлено на поддержку произвольных ID и совместимости с токенами клиента: `/^fake-(?:jwt-)?token-(?:for-)?(.+)-(\d+)$/`.
2. **Дублирование middleware в `backend/server.js`**:
   - Удалены повторные вызовы `app.use(cors())`, `app.use(express.json())`, `app.use('/api/v1/auth')`, `app.use('/api/v1/students')`.
   - Логирование запросов упорядочено перед маршрутами.
   - Добавлен глобальный middleware обработки 500-ошибок.
3. **Новый эндпоинт сессии**:
   - В `backend/routes/auth.js` добавлен эндпоинт `GET /api/v1/auth/me` для проверки текущего авторизованного профиля по заголовку `Authorization: Bearer <token>`.
4. **Серверный экспорт отчетов**:
   - В `backend/routes/reports.js` добавлены эндпоинты `GET /api/v1/reports/export/subject` и `GET /api/v1/reports/export/debtors`, отдающие сформированные CSV-файлы в кодировке UTF-8 с BOM (нативная поддержка русского языка в MS Excel).

### 1.3. Сопряжение фронтенда и бэкенда
1. **Vite Proxy (`vite.config.js`)**:
   - Настроен прокси `/api` -> `http://localhost:5000`, исключающий проблемы с CORS и междоменными запросами при разработке.
2. **Универсальный API-клиент (`src/js/api/client.js`)**:
   - `API_BASE_URL` автоматически выбирает относительный путь `/api/v1` при запуске через Vite (порт 3000), либо обращается напрямую к `http://localhost:5000/api/v1`.
   - Режим `USE_MOCK` установлен в `false` (работает реальный Express-бэкенд).
   - В сайдбаре (`src/js/app.js`) динамически отображается статус текущего режима: зеленый индикатор и подпись `Express API активен (:5000)`.
3. **Корневые скрипты (`package.json`)**:
   - Добавлены команды для удобного запуска:
     - `npm run server` — запуск бэкенда на порту 5000 (`node backend/server.js`);
     - `npm run server:dev` — запуск бэкенда с автоперезагрузкой (`node --watch backend/server.js`);
     - `npm run dev` — запуск фронтенда Vite на порту 3000;
     - `npm run seed` — перезаполнение базы данных SQLite.

## 2. Чего не хватает для бэкенда (Roadmap & Рекомендации)

Ниже систематизирован список доработок, необходимых для приведения бэкенда к профессиональному уровню и уверенной защиты лабораторной/курсовой работы.

### Блок 1. Безопасность и аутентификация (Высокий приоритет)
1. **Реальный JWT (JSON Web Token)**:
   - *Проблема:* Сейчас сервер генерирует временную строку вида `fake-token-u-1-...`. Токен не подписан криптографическим ключом, не имеет встроенного срока годности (TTL) и может быть подделан.
   - *Решение:* Установить пакет `jsonwebtoken` (`npm i jsonwebtoken`), вынести `JWT_SECRET` в конфигурацию и подписывать полезную нагрузку (`{ id, role, username }`) с ограничением жизни (например, `expiresIn: '8h'`).
2. **RBAC-авторизация на уровне роутов Express**:
   - *Проблема:* На фронтенде есть разделение прав (студент не видит кнопки админки), но бэкенд не защищал маршруты. Любой клиент мог отправить `DELETE /api/v1/admin/users/u-2` или `PUT /api/v1/grades/cell` без проверки роли.
   - *Решение:* Внедрить созданный middleware `requireRole(['admin'])` на роуты админки, `requireRole(['teacher', 'admin'])` на выставление оценок и `requireRole(['dean', 'admin'])` на изменение справочников.
3. **Эндпоинт смены пароля**:
   - Добавить маршрут `POST /api/v1/auth/change-password` с проверкой старого пароля и хешированием нового через `bcryptjs`.
4. **Rate Limiting и защита от перебора (Brute-force)**:
   - Подключить `express-rate-limit` на роут `POST /api/v1/auth/login` (максимум 5-10 попыток в минуту).

---

### Блок 2. Архитектура базы данных и целостность (Средний/Высокий приоритет)
1. **Каскадное удаление (ON DELETE CASCADE) для таблицы `grades`**:
   - *Проблема:* В схеме `CREATE TABLE grades` нет внешних ключей `REFERENCES disciplines(id) ON DELETE CASCADE` и `REFERENCES students(id) ON DELETE CASCADE`. При удалении дисциплины или студента оценки могут зависнуть в базе (orphaned records).
   - *Решение:* Добавить внешние ключи и активировать `PRAGMA foreign_keys = ON;`.
2. **Переход с синхронного `node:sqlite` на асинхронный пул или стабильный драйвер**:
   - *Проблема:* Встроенный модуль `node:sqlite` (`DatabaseSync`) является экспериментальным в Node.js 22/24 (выводит `ExperimentalWarning`) и работает синхронно, блокируя поток событий Node при тяжелых запросах.
   - *Решение:* Для продакшна использовать `better-sqlite3` или PostgreSQL (`pg` + `knex` / `prisma`).
3. **Транзакционность операций**:
   - При добавлении студента выполняется два запроса: `INSERT INTO students` и `UPDATE groups SET studentCount = studentCount + 1`. Их необходимо оборачивать в транзакцию (`db.exec('BEGIN') ... COMMIT`), чтобы исключить рассинхронизацию при ошибках.

---

### Блок 3. Полнота API-контрактов и DTO
1. **Серверная пагинация (Pagination & Filtering)**:
   - *Требование из ТЗ:* Контракты DTO должны поддерживать пагинацию (`page`, `pageSize`, `totalCount`, `totalPages`).
   - *Текущее состояние:* Эндпоинты `GET /api/v1/students` и `GET /api/v1/admin/users` отдают все записи единым массивом.
   - *Решение:* Добавить query-параметры `?page=1&pageSize=10&sortBy=fullName&sortOrder=asc` и возвращать объект метаданных пагинации.
2. **Пакетное выставление оценок (`POST /api/v1/grades/batch`)**:
   - Сейчас доступно только изменение одной ячейки `PUT /api/v1/grades/cell`. Для массового сохранения целого занятия или ведомости нужен пакетный метод.
3. **Жизненный цикл ведомостей (Статусы)**:
   - Добавить таблицу `statements` (ведомости) со статусами: `Черновик` -> `На подписи` -> `Закрыта`. После закрытия ведомости запрещать редактирование оценок в журнале.
4. **Фильтрация журнала аудита**:
   - В `GET /api/v1/admin/audit-logs` добавить фильтры по `userId`, `action`, `startDate`, `endDate`.

---

### Блок 4. Валидация и коды ошибок (REST Best Practices)
1. **Схемы валидации входящих данных (Zod / Joi)**:
   - Вместо ручных проверок `if (!body.fullName)` использовать декларативную валидацию схем с возвратом массива детализированных ошибок по полям.
2. **Стандартизация HTTP-кодов состояний**:
   - Ошибки клиентского ввода должны возвращать `400 Bad Request` или `422 Unprocessable Entity`.
   - Неавторизованный доступ — `401 Unauthorized`.
   - Недостаток прав роли — `403 Forbidden`.
   - Отсутствующая запись — `404 Not Found`.
   - Конфликт уникальности (например, логин уже занят) — `409 Conflict`.

---

### Блок 5. Конфигурация, Документация и DevOps
1. **Переменные окружения (`.env`)**:
   - Вынести порт (`PORT=5000`), путь к БД (`DB_PATH`), разрешенные хосты CORS в файл конфигурации с использованием библиотеки `dotenv`.
2. **Документация API (Swagger / OpenAPI)**:
   - Подключить `swagger-ui-express` и спецификацию `openapi.yaml` по маршруту `GET /api/docs`. Это произведет сильное впечатление на защите проекта.
3. **Автоматические тесты**:
   - Написать интеграционные тесты для API через `supertest` и `vitest` (проверка логина, создания студента, выставления оценки и расчета GPA).
